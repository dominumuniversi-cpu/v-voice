# Архитектура VoiceTranscribator

Дата: 26.11.2026 · Статус: черновик · Связано с [VOICE-TZ.md](../SPECS/VOICE-TZ.md)

## 1. Принципы

1. **Телефон — только «уши» и экран.** Запись, буфер, живой текст. Всё тяжёлое (диаризация, LLM,
   хранение) — на сервере. Модели не привязываются к приложению — замена провайдера на сервере.
2. **Провайдеры за интерфейсом.** ASR / диаризация / LLM — порты; реализации — адаптеры.
   Смена «GigaAM ↔ Speechmatics ↔ Deepgram» — правка конфига, а не кода.
3. **Сырое аудио — источник истины.** Онлайн-транскрипт приблизителен; финальный проход по всему файлу
   даёт точность. Данные не теряются никогда: локальный буфер + догрузка.
4. **Схема разбора — контракт.** LLM отвечает строго по JSON-схеме; валидатор + evidence-правило.
5. **Никаких секретов в приложении.** Ключи провайдеров хранятся на сервере/в vault, а не в аппаре.

## 3. Поток данных

1. Пользователь жмёт «Слушаю», приложение проверяет разрешения, запускает нативный сервис записи.
2. Каждые 100–300 мс аудио идёт в VAD (на устройстве). Речь → очередь; тишина → выброс (учёт в статистике).
3. Сегменты по 1–5 c уходят по WebSocket на `/live`; сервер стримит их в выбранный ASR-адаптер.
4. ASR возвращает `volatile` (приблизительный) и `final` фрагменты с `start_s/end_s`; финальные
   отправляются в приложение и в БД.
5. Параллельно сервер помечает фрагменты диаризацией (окна 5 c) — `speaker_id`.
6. Каждые 2–3 минуты — **инкрементальный разбор**: новые реплики → LLM → дельта выжимки/задач
   (пользователь видит «уже 2 задачи»).
7. По завершении: полный файл → точный ASR → точная диаризация → **итоговый LLM-разбор** с evidence.
8. Пользователь одобряет задачи → сервер шлёт в задачник, ставит напоминания, отдаёт вебхук.

## 4. Модели данных (PostgreSQL)

| Таблица | Назначение |
|---|---|
| `users` | пользователь, настройки, пресет |
| `voiceprints` | отпечаток голоса владельца/участников (вектор, хранится отдельно от аудио) |
| `sessions` | запись: статус, язык, провайдеры, длительность, стоимость |
| `segments` | фрагмент: `session_id`, `start_s`, `end_s`, `text`, `speaker_id`, `confidence`, `is_volatile` |
| `speakers` | спикер внутри сессии: `display_name`, `verdict` (owner/member/foreign/noise) |
| `digests` | выжимка: `summary`, `decisions`, `open_questions`, `model`, `version` |
| `items` | задачи/встречи/напоминания: `kind`, `title`, `owner`, `due_at`, `evidence` (jsonb), `status` |
| `integrations` | куда и что отправляется (helper, CRM), креды |
| `usage` | расход: минуты ASR, токены LLM, деньги |

## 5. API v1 (черновик)

```
POST   /api/v1/auth/login                      → JWT
GET    /api/v1/sessions
POST   /api/v1/sessions                        {"lang":"ru","preset":"balanced"}
POST   /api/v1/sessions/{id}/chunks            multipart audio
GET    /api/v1/sessions/{id}/segments?from_s=
GET    /api/v1/sessions/{id}/digest
POST   /api/v1/sessions/{id}/digest/rebuild
POST   /api/v1/sessions/{id}/items/{item}/approve   → отправка в задачник
GET    /api/v1/providers  POST /api/v1/providers/{p}/test  (проверка ключа)
WS     /api/v1/sessions/{id}/live
```

Формат сегмента:
```json
{"start_s": 12.4, "end_s": 15.1, "speaker": "S2", "text": "Я отправлю смету завтра утром",
 "confidence": 0.93, "volatile": false}
```
Формат элемента разбора (задача):
```json
{"kind":"task","title":"Отправить смету Анне","owner":"Дмитрий","due_at":"2026-11-27T08:00:00+05:00",
 "priority":"high","evidence":{"start_s":742.0,"end_s":746.5,
 "quote":"Я отправлю смету завтра утром, успеем"}}
```

## 6. Ключевые технические решения (ADR)

| ADR | Решение |
|---|---|
| ADR-0001 | Flutter-оболочка + нативные мосты записи (запись в фоне — только нативная) |
| ADR-0002 | Провайдер ASR сменный, дефолт — self-host GigaAM-v3 e2e_rnnt |
| ADR-0003 | LLM-разбор со строгой JSON-схемой и evidence-правилом |
| ADR-0004 | Диаризация: MVP — серверные окна (pyannote), фаза 2 — онлайн |
| ADR-0005 | Хранение аудио — S3-совместимое, удаление по сроку; отпечатки голоса отдельно |

## 7. Ограничения платформ (обязательно понимать команде)

| Ограничение | Что делаем |
|---|---|
| iOS: фоновый аудиорежим описан как воспроизведение звука | не обещаем бессрочную фоновую запись; буфер на диск каждые 1–2 c; честный статус в UI; отдельная задача «живой прогон фона» |
| iOS: App Store может отклонить за «запись без воспроизведения» | вариант: локальное воспроизведение в режиме «конференция» (тихий канал) — согласовать, проверить на ревью |
| Android 14+: сервис микрофона стартует только из видимого UI | всегда старт из кнопки; обработка `ForegroundServiceStartNotAllowedException` |
| Android: уведомление о записи обязательно | канал уведомления с «пауза/стоп» |
| iPhone, звонки | не пишем системный звук звонка (нужен CallKit) — out of scope MVP |

## 8. Безопасность и приватность

- Аудио и транскрипты — персональные данные: шифрование в покое (S3 SSE), TLS в транспорте.
- Ключи провайдеров — только на сервере, в dsh-vault / env.
- Срок хранения: аудио — настраиваемый (по умолчанию 30 дней), транскрипт — пока сессия жива.
- Отпечатки голоса — отдельная таблица, удаляются за 1 клик, не экспортируются.
- Экспорт и удаление по запросу пользователя (задача фазы 4).
